# Change workflow

1. 用一句话写目标，再写明确的不做项和成功/失败判定。
2. 在改动前列出入口、调用方、数据、权限、配置和部署影响。
3. 先添加或确认能复现问题的最小测试，再实现最小修复。
4. 失败时保留原始错误与上下文，按输入、逻辑、依赖、环境逐层排查。
5. 运行最小验证门槛和受影响回归，交付时列出证据与未验证风险。

## 决策路由

- 需求不清时先问目标、边界、约束、数据和验收；存在取舍时给出方案与影响。
- 变更前写验证门槛，变更后先跑最小验证，再按调用链、数据和部署边界回归。
- 排障先确认复现和实际运行版本；一次只改变一个变量，根因未明不得用默认值或宽泛 catch 压制异常。
- 提交前按后端、前端、数据库、权限、配置和发布交叉检查，问题按严重程度与证据分级。
- 版本控制操作遵循当前任务的分支和保护规则；冲突逐块解决，交付说明事实、证据和剩余风险。
